# Changelog

All notable changes of `csp-workflow` are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the versions follow
[Semantic Versioning](https://semver.org/). A release is a `release/<version>` branch cut from `main` and filled with the commits of `qa`,
re-applied with `git cherry-pick -x` (numerals 6.2.3, 10 and 11 of the course norm); it reaches `main` by pull request, never by merging `qa`,
and is tagged `v<version>` once it is merged.

## [Unreleased]

### Changed

- The README and the CODEOWNERS comments carry the identity of the project (Cinesync Platform, team `cinesync-platform`, Group 1, documentation in `csp-docs`) instead of the template identity. The owner of `*` is unchanged.

### Added

- The end-to-end test also proves the failure of a compensation (HU-CONCESSIONS-004, last open box of Annex E, code-corhuila/csp-workflow#1): while the proxy holds a confirm back, a trigger of the disposable database makes every update of a reservation fail, so the real Booking answers `500` to the confirm and to the release of the compensation (three attempts each, same key); the saga ends `FAILED` with `failedStep` `confirm-reservation`, the hold stays `HELD`, the answer carries no detail and a restart of the workflow leaves the saga alone. The participant timeout of the test platform is 30 s and the held confirms last 6 s, because the gateway gives up after 10 s.
- The saga keeps the correlation id of its request (HU-CONCESSIONS-004, ADR-065, code-corhuila/csp-workflow#1): the new migration `V006` adds `correlation_id` to `workflow.saga` (nullable, because the sagas stored before it have none, with the named check `chk_saga_correlation_id_length` that bounds it to the 128 characters the service accepts; reversion `U006`). `SagaController` takes the id from the request, the command, `SagaInstance` and `SagaSnapshot` carry it, both stores keep it, and `BookingParticipant` receives it on every call, so `RunBookSeatsSaga` sends the one of the original request in the steps it repeats after a restart and in the compensation, where it used to send a new one. `HttpBookingParticipant` no longer reads the logging context. A saga without a stored id (stored before `V006`) uses its own id, which is stable across restarts. The CI step that applies the migrations expects six.

- End-to-end test of the saga `book-seats` against the real `csp-booking-api` and `csp-catalog-api` (HU-CONCESSIONS-004, last box of Annex E, code-corhuila/csp-workflow#1): `tests/e2e/up.sh` starts a disposable copy of the platform (Compose project `csp-e2e`, `origin/develop` of the sibling repositories and this commit of the workflow, random credentials, a throwaway key pair) and seeds Catalog with a movie, a room and a showtime through its administration routes; `tests/e2e/book-seats.sh` runs the checks and prints the totals of passed and failed; `tests/e2e/down.sh` removes everything. The checks cover the happy path, the compensation of a confirmation that fails, idempotency, the service credential, the key `<sagaId>:<step>` and the correlation id that Booking receives, the absence of the failure detail in the answer, the input errors and the recovery of a saga cut by a restart. A recording proxy between the workflow and Booking logs what Booking does not (it forwards every call untouched) and, while Booking `develop` requires `movieTitle` and `roomName` in the internal hold against its contract, adds them; the script prints `KNOWN BOOKING DEFECT` when it does. The README explains how to run it.

- The compose file takes its variables from the platform environment (HU-CONCESSIONS-004): `SERVICE_TOKEN` and `SPRING_DATASOURCE_USERNAME` already belong to `csp-worker` and `csp-booking-api` in the file the platform shares, so `deploy/compose.yml` reads `WORKFLOW_SERVICE_TOKEN`, `WORKFLOW_APP_USER` (default `workflow_app`) and `WORKFLOW_APP_PASSWORD` and hands them to the service under the names it reads. `.env.example` lists the compose variables. The new migration `V005` makes the login `workflow_app` a member of `workflow_writer` when that login exists, which `csp-infra-postgres` creates before the migrations run (reversion `U005`). The CI renders the compose file with the variables of the platform, and refuses it without the token.
- Recovery of the sagas a restart cut in the middle (HU-CONCESSIONS-004, ADR-065, closes code-corhuila/csp-workflow#7): `RecoverSagas` and `RunBookSeatsSaga.recover` resume, when the service starts, every saga that was running and last changed before the process started (`SagaStore.findRunningUpdatedBefore`, served by the partial index `idx_saga_running_updated_at` of the new migration `V004`). The orchestrator now runs the steps that are not completed yet: a saga cut before its first call, during the hold, after it, during the confirmation or during its compensation goes on from there, with the same key `<sagaId>:<step>`, so no step is applied twice. A saga another writer already moved is skipped (`StaleSagaException`) and one that fails does not stop the others; the result is logged by `SagaRecoveryRunner`. A test with two processes on one PostgreSQL shows a saga cut during the confirmation finished by the next process.
- PostgreSQL saga store (HU-CONCESSIONS-004, ADR-065 amended, code-corhuila/csp-workflow#7): `db/` with the Flyway migrations (`V001` schema `workflow`, `V002` table `saga` with named constraints and `uq_saga_user_id_idempotency_key`, `V003` the role `workflow_writer`) and their reversions, `JdbcSagaStore` (insert with version 1, updates guarded by the version, `StaleSagaException` for an old writer) and the tooling service `workflow-db-migrate` in `deploy/compose.yml`. Two starts with the same user and key that arrive together are decided by the unique constraint: the loser answers as a replay (`SagaAlreadyStartedException`). The service now needs `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD`; the in-memory store remains only for tests (`workflow.state.store=memory`). The CI runs the store tests against PostgreSQL, applies the migrations with the tooling image and starts the image with the database. The recovery of the sagas a restart cut comes in the next pull request.
- The saga keeps what it was asked to do and can be restored (HU-CONCESSIONS-004, ADR-065, code-corhuila/csp-workflow#7): `SagaInput` (the showtime and the seats, with the fingerprint that tells a replay from another request that reuses the key), `SagaSnapshot` with every field of a saga, `SagaInstance.restore` and `snapshot`, and a `version` that the store records with `persistedAs`. A store can now persist a saga and give it back in the same state, which a restart needs to repeat a step or to compensate. No behavior change: the PostgreSQL store follows.
- Endpoints of the saga `book-seats` (HU-CONCESSIONS-004, ADR-066, `workflow-service.yaml` 1.0.0): `POST /api/v1/sagas/book-seats` (`Idempotency-Key` required: `201` with `Location` on the first call, `200` with the same saga on a repeat, `409` for another payload; the body is validated field by field and a `userId` in it is rejected) and `GET /api/v1/sagas/{id}` (`404` for an unknown saga or one of another user). The answer names `failedStep` and never the internal detail. The service is composed in `workflow-app` with the filters, the Booking client and an in-memory saga store; it refuses to start without `JWT_PUBLIC_KEY` or `SERVICE_TOKEN`. New variables: `BOOKING_API_URL`, `JWT_PUBLIC_KEY`, `SERVICE_TOKEN`, `HTTP_ATTEMPTS`, `HTTP_TIMEOUT_SECONDS`, `HTTP_BACKOFF_MS`. The CI step of the image now starts it with a throwaway key pair.
- Booking participant (HU-CONCESSIONS-004, ADR-035, ADR-066): `HttpBookingParticipant` implements the port with the internal operations `POST /internal/workflow/holds`, `.../reservations/{id}/confirm` and `.../release`. Every call carries the credential of the workflow (`ServiceToken`, read again at every call from `SERVICE_TOKEN_FILE` or fixed in `SERVICE_TOKEN`), `Idempotency-Key: <sagaId>:<step>` and the `X-Correlation-Id` of the request, with a bounded timeout and retries with full jitter only on network errors, `429` and `5xx` (`RetryingHttp`). A refusal or an unreachable service becomes a `ParticipantFailedException` that keeps only the status and the error code. Not composed yet: the wiring and the configuration come with the endpoints.
- Security and error layer of the HTTP entry (HU-CONCESSIONS-004, ADR-066): `Rs256Verifier` (RS256 only, `exp` and `sub` required, 30 seconds of leeway, `aud` as a string or a list), `AuthFilter` (401 `UNAUTHORIZED` without token, 401 `INVALID_TOKEN` for an invalid, expired or non-UUID-subject token, 403 `FORBIDDEN` for a service credential, and the user id read from the `sub`; `/health` needs no token), `CorrelationFilter` (reuses or creates `X-Correlation-Id`, one access line per request) and `ErrorHandler` with the common envelope. Not composed yet: the saga endpoints and the wiring come in the next pull request.
- Domain `saga` and the orchestrator of the saga `book-seats` (HU-CONCESSIONS-004, ADR-066): `SagaInstance` with its state machine (`RUNNING`, `COMPLETED`, `COMPENSATED`, `FAILED`), the ports (start and get a saga, the Booking participant, the saga store, the id generator) and `RunBookSeatsSaga`, which holds the seats, confirms the reservation, saves the state before and after every step, sends the key `<sagaId>:<step>` to every call, releases the hold if the confirmation fails and ends `FAILED` if the release fails. The same user, key and request return the first saga and run nothing. No adapter yet: the participant, the store and the HTTP entry come in the next pull requests.
- Base structure of the repository (Annex E, ADR-064): three Maven modules (`workflow-core`, `workflow-adapters`, `workflow-app`), the liveness endpoint `GET /api/v1/health`, `deploy/Dockerfile` and `deploy/compose.yml`, `.env.example` and the `ci.yml` workflow. The saga is not implemented yet.
